A free website, hosted on GitHub Pages, where the content is a complete
browser game invented from scratch by AI and rebuilt from nothing once a
day. Every visitor that day plays the same game; the next day it is
replaced by something completely different. Visitors can also bring
their own API key and have a model of their choice build a game in front
of them.

The project is complete and running: daily generation, moderation and
smoke testing, the history and feedback loop, the front-end viewer,
bring-your-own-key mode and error reporting are all live.

## How a day's game is made

A GitHub Actions workflow runs the generation pipeline once a day. It
works through a rotation of free models on OpenRouter, giving each one at
most one attempt. Every attempt:

1. picks the next model in the rotation
2. builds a prompt from the content guardrails, the genre catalog, a
   digest of recent games, and the specific reason the previous attempt
   failed
3. asks the model for a single self-contained HTML game and extracts it
   from the response
4. **moderates** it, with a local keyword scan and then a second model
   judging it against the same guardrails the generator was given
5. **smoke tests** it in headless Chromium: the game must load, draw
   something, throw no uncaught errors, and make no network requests at all

The first attempt to pass both gates is published. If every model fails,
that is treated as a normal outcome rather than an error: the run records
the failure, leaves yesterday's game live, and finishes green.

Both gates **fail closed**. An unreachable moderator, an ambiguous
verdict, an unparseable response or a page that won't load all count as
rejections, because a false rejection costs one retry while a false
acceptance would publish unvetted content to a public site.

## Publishing on time

GitHub defers scheduled workflows under load, often by hours. So the
punctual trigger is an external cron service that dispatches the workflow
at the moment the game is due, and the workflow's own schedule runs an
hour later as a fallback for any day the external trigger misses. When
both fire, the second run finds the day already published and stops, so
visitors never see a game swapped out from under them.

The daily run commits the new game to `main`, which triggers a separate
deploy workflow. That workflow builds the front-end and assembles it with
the committed game archive into the site GitHub Pages serves.

## The site

A small React app styled with Tailwind and built with Vite. It reads a
manifest naming the day's game and loads that game into an
`<iframe sandbox="allow-scripts">` without `allow-same-origin`, so the
AI-written code is isolated from the page and cannot reach its storage or
navigate it. That sandbox is the trust boundary; React only renders the
surrounding page, where JSX escaping handles the model-written title and
description.

Around the game, the page shows a countdown to the next one, the model
that wrote it, and a light/dark theme toggle. Visitors can like or
dislike a game, choosing from a fixed list of reasons when they dislike
it.

**Bring your own key.** A visitor can paste their own key for OpenRouter,
Anthropic, OpenAI or Gemini and replay that day's exact prompt against a
model of their choice. The response streams into the page as it is
written, then runs in the same sandbox as the daily game. The key stays
in the browser and goes only to the provider it belongs to.

## Learning from history

Every attempt, published or not, is recorded in a history file: which
model ran, whether it passed, why it failed, and how visitors reacted.
That history feeds back into generation in three ways:

- recent games are summarised into the prompt, so the model avoids
  repeating a theme or mechanic it has used lately
- recurring failure kinds and dislike reasons map to fixed corrective
  instructions, written by the project rather than quoted from visitors
  or earlier models
- after each run, a reflection step asks a model to distil the recent
  window into a short lessons note that later prompts include

A rollup step moves older entries into monthly archive files and derives
summary tallies from the full archive, so the history the prompt reads
stays small while no day is ever lost.

## How it was built

- **TypeScript throughout.** The pipeline runs directly on Node's native
  type stripping, with no build step. Code shared by the pipeline and the
  browser lives in one isomorphic module compiled by both.
- **A mock at one seam.** A single module decides between the real
  OpenRouter client and a fixture-backed mock, so the whole pipeline runs
  end to end locally with no API key and no code path that differs from
  production.
- **Testing.** `node --test` covers the pipeline, Vitest with Testing
  Library covers the front-end, and Playwright drives headless Chromium
  for the smoke tests. CI enforces coverage thresholds.
- **Continuous integration.** Every pull request and push to `main` runs type
  checking, ESLint, Prettier, validation of every hand-edited config and
  history file, the full test suite with coverage, and a production build.
  A separate workflow scans what ships to visitors for leaked secrets.
- **Error reporting.** Sentry captures errors from the page and, through a
  snippet added at publish time, from inside each game's sandbox.
- **Free infrastructure.** Free models through OpenRouter, GitHub Actions
  and Pages, Sentry's free plan, cron-job.org and Supabase.

## Configuration

The rules the pipeline follows live in plain files, separate from code:

- `config/guardrails.md` holds the content rules, injected word for word
  into both the generation and moderation prompts so the two cannot drift
  apart
- `config/genres.json` is the genre catalog the model chooses from
- `config/models.json` is the model rotation, where each model can be
  switched off without being removed
- `config/generation.json` sets the publish time, sampling temperature,
  remix odds and history window size
- `config/byokModels.json` lists the providers and models offered in
  bring-your-own-key mode
