The whole pipeline also runs locally against a mock OpenRouter client with

## How the pipeline works

Each daily run makes up to three attempts. Every attempt:

1. picks the next model in rotation from `config/models.json`
2. builds a prompt from `config/guardrails.md` (verbatim), the genre
   catalog, and a digest of recent games, plus the previous attempt's
   specific failure reason
3. calls OpenRouter and extracts the response's two fenced blocks
4. **moderates** it — a local keyword scan, then a second AI call judging
   it against the guardrails
5. **smoke tests** it in headless Chromium — no uncaught JS errors, and no
   outbound network requests at all

If all three attempts fail, that's a normal outcome: the run logs a
`failed_kept_previous` history entry, leaves the live site untouched, and
still exits green.

Both the moderation and smoke-test layers **fail closed** — an unreachable
moderator, an ambiguous verdict, or an unparseable response is treated as
a rejection. A false rejection costs one retry; a false acceptance would
publish unvetted content to a public site.

## The site

A small React + Tailwind app, built with Vite. It fetches `manifest.json`,
then loads that day's bundle into an `<iframe sandbox="allow-scripts">` —
with no `allow-same-origin`, so the AI-authored game is fully isolated from
the page and can't reach its storage. That iframe is the real trust
boundary; React only renders the surrounding chrome, where JSX escaping
handles the AI-generated title, genre and model text.

## Development

Requires Node 23.6+ (the pipeline is TypeScript, run directly via Node's
native type stripping — no `ts-node`, and no build step for the pipeline).

```
npm install
npx playwright install chromium   # for the smoke tests
npm run dev                       # front-end dev server
npm test                          # run the test suite
npm run typecheck                 # both Node and browser projects
npm run dry-run                   # full pipeline against mock responses
npm run build:site                # build + assemble the deployable site
```

`npm run dev` serves the real files the pipeline writes, so after a dry run
you can play the generated game locally at the same URLs production uses.

`npm run dry-run` needs no credentials: `scripts/lib/get-client.ts`
returns the real OpenRouter client when `OPENROUTER_API_KEY` is set and a
fixture-backed mock otherwise, so the same code path runs either way. It
writes a real archive folder, `manifest.json` and history entry, which is
the easiest way to see the pipeline's output end to end.

## Deployment

`deploy-pages.yml` builds the app and publishes it to GitHub Pages on every
push to `main`. Because there's a build step, the site is assembled rather
than served from the repo: `scripts/assemble-site.ts` merges the built app
in `dist/` with the committed `manifest.json` and `games/archive/**`.
Pages must therefore be configured with **GitHub Actions** as its source,
not "deploy from a branch".

**Note:** `config/generation.json`'s `cronSchedule` must be kept manually
in sync with the `on.schedule.cron` value in
`.github/workflows/generate-daily-game.yml` — GitHub Actions `on:`
triggers can't reference external config, so this value is duplicated by
hand in both places.

## Editing the game rules

These files are meant to be hand-edited without touching code:

- `config/guardrails.md` — the content rules, injected verbatim into both
  the generation and moderation prompts so the two can never drift apart
- `config/genres.json` — the genre catalog the model chooses from
- `config/models.json` — the OpenRouter model rotation (flip `active` to
  disable one without removing it)
- `config/generation.json` — retry temperatures, remix odds, history
  window size
